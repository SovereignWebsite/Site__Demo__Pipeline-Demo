pipeline-demo.sovereignweb.site

A site from one request

This site is the worked example of the Sovereign Website pipeline, and its documentation. It was made from one small file, a request, and everything after that was done by the pipeline: a repository, an address, HTTPS, and a first page.

The path of one request

  1. A request folder. requests/<date>__<label>/site.json in the Factory names the site: its label, title, description and kind. It reaches the dev branch only with Dinis Cruz's merge.
  2. Checks. Every push to dev runs the tests, the policy validation, a leak scan, the signed-commit check and a dry plan of the organisation against the policy.
  3. Org apply. A push to dev that changes requests/ runs Org apply (it also runs every hour). It creates the repository Site__<label> from the site template, with Pages on, the custom domain, the agents' team with push, and two rulesets: main is locked, dev is safe.
  4. DNS apply. The same push runs DNS apply, which writes a CNAME for <label>.sovereignwebsite.site in Route 53, through a short-lived AWS role and no stored keys.
  5. HTTPS. GitHub issues a certificate for the address; the hourly Org apply then enforces HTTPS.
  6. Publish. In the new repository, every push to dev deploys the site/ folder to GitHub Pages.

What the owner holds

The site is static files in a repository. Its files, its history and its address can move anywhere, at any time. There is no server code, no cookies and no tracking. The pipeline never deletes: a request removed from the Factory leaves its repository and address in place, to be retired by hand.

Who does what

Agents do the work and people decide. Each agent signs every commit with its own published key and names its session; the Factory's Agent Behaviour Policy lists what each agent may change, and anything not listed is refused. Changes reach main only when Dinis merges them.
